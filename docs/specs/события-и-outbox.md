# События банка: outbox и доставка через RabbitMQ

Статус: сделано (этап 5).

Связано: план [события-и-outbox.md](../plans/события-и-outbox.md); потребитель событий — [Telegram](уведомления-в-telegram.md).

## Цель

Этап 5 роадмапа. Банковские операции публикуют события в брокер сообщений так, чтобы событие не терялось и не появлялось без операции, даже если брокер или процесс упали. Событие записывается в БД в той же транзакции, что и операция (outbox), а отдельный воркер доставляет его в RabbitMQ. Мини-потребитель принимает события и доказывает доставку и идемпотентность; на этапе 6 его заменит сервис уведомлений.

## Решения

- Подход: собственный outbox поверх EF Core/PostgreSQL и `RabbitMQ.Client`, без MassTransit, Wolverine и CAP: паттерн должен быть виден в коде.
- Гарантия доставки: at-least-once. Дубли возможны, поэтому потребитель дедуплицирует по `eventId`.
- События этапа: `TransferCompleted` и `AccountDeposited`. События регистрации и пароля, Telegram и реестр схем вне объёма.

## События

Конверт (JSON, UTF-8, `contentType: application/json`):

- `eventId` (Guid) — равен id строки outbox, ключ дедупликации;
- `type` — `transfer.completed` или `account.deposited`;
- `version` — целое, сейчас `1`;
- `occurredAt` — время операции (UTC, ISO 8601);
- `data` — полезная нагрузка.

`TransferCompleted.data`: `transferId`, `fromAccountId`, `toAccountId`, `fromOwnerId`, `toOwnerId`, `amount` (минорные единицы, целое), `currency`.
`AccountDeposited.data`: `transferId`, `accountId`, `ownerId`, `amount`, `currency`.

В событиях нет email, имён и токенов: потребитель по `ownerId` получит нужное сам.

## Outbox (Domain/Application/Infrastructure)

- Таблица `outbox_messages`: `id` (uuid, PK), `type`, `version`, `payload` (jsonb), `created_at`, `occurred_at`, `attempts` (int), `next_attempt_at`, `published_at` (null до отправки), `dead_at` (null, ставится после исчерпания попыток), `last_error` (текст без чувствительных данных, обрезается). Частичный индекс по `next_attempt_at` для строк, где `published_at IS NULL AND dead_at IS NULL`.
- `IOutbox.Add(IntegrationEvent)` в Application; реализация добавляет строку в контекст EF. `TransfersService.TransferAsync` и `DepositAsync` вызывают её внутри существующей транзакции (`ExecuteInTransactionAsync`), перед `SaveChanges`. Идемпотентный повтор запроса (ответ из `IdempotencyStore`) событие второй раз не создаёт.
- Откат операции откатывает и событие: отдельной записи вне транзакции нет.

## Воркер публикации (`OutboxPublisher`, `BackgroundService` в API)

- Цикл: в транзакции выбрать пачку (например, 50) строк `WHERE published_at IS NULL AND dead_at IS NULL AND next_attempt_at <= now ORDER BY created_at FOR UPDATE SKIP LOCKED`; несколько экземпляров API не отправляют одно и то же событие дважды одновременно.
- Публикация в обменник `minibank.events` (topic, durable), routing key = `type`, `persistent: true`, `messageId = eventId`, с publisher confirms. Строка помечается `published_at` только после подтверждения брокера; транзакция коммитится после пачки.
- Ошибка публикации: `attempts++`, `next_attempt_at` = now + экспоненциальная задержка с потолком (например, 5 с … 5 мин), `last_error`. После `MaxAttempts` (по умолчанию 10) строка получает `dead_at` и остаётся для разбора.
- Падение между подтверждением брокера и коммитом даёт повторную отправку (дубль), что допустимо при at-least-once.
- Пауза между пустыми циклами — опрос раз в секунду (`Events:PollInterval`); без брокера API работает, события копятся в таблице.
- Публикатор включается настройкой `Events:Enabled`; при `false` (например, в тестах без брокера) воркер не стартует, а события всё равно пишутся в outbox.
- Очистка: опубликованные строки старше `Events:RetentionDays` (по умолчанию 7) удаляются тем же воркером небольшими пачками.

## Брокер и потребитель

- RabbitMQ в Compose (`rabbitmq:management`, UI на `15672`, AMQP только внутри сети; healthcheck).
- Топология объявляется идемпотентно и издателем, и потребителем: обменник `minibank.events`, очередь `minibank.notifications` (durable) с привязкой `#`, `x-dead-letter-exchange` на `minibank.events.dead`, очередь `minibank.notifications.dead`.
- Потребитель — новый проект `MiniBank.Notifications` (worker service, свой образ и сервис в Compose). Читает очередь с ручными подтверждениями, `prefetch` ограничен.
- Идемпотентность: в собственной схеме/БД потребителя (та же инстанция PostgreSQL, отдельная база или схема `notifications`) таблица `processed_events(event_id PK, processed_at)`. Обработка и вставка в `processed_events` идут в одной транзакции; повторный `eventId` подтверждается без обработки.
- Обработка пока: структурный лог и запись в таблицу `received_events` (тип, время, `ownerId`). Ошибка обработки: `nack` без возврата в очередь, сообщение уходит в dead-letter очередь после повторных попыток (ограниченное число через счётчик в заголовке). Неизвестный `type` или версия — логируется и подтверждается, чтобы не блокировать очередь.
- Контракт событий (классы конверта и данных) лежит в общем проекте `MiniBank.Contracts`, на который ссылаются API и потребитель.

## Надёжность и наблюдаемость

- Недоступность RabbitMQ не ломает переводы: публикатор ловит исключения, подключение восстанавливается автоматически.
- Готовность `/health` остаётся про БД и от брокера не зависит. Публикатор пишет в лог уровня Warning, если самая старая неотправленная строка старше порога (`Events:StaleAfter`, по умолчанию 5 минут), и считает такие строки; наружу эти данные не отдаются.
- В логах нет полезной нагрузки событий целиком: только `eventId`, `type`, номер попытки.
- Настройки (`Events:*`, `RabbitMq:*`) валидируются при старте.

## Тесты

- Домен/Application: перевод и пополнение добавляют ровно одно событие нужного типа с верными данными; откат (недостаточно средств, чужой счёт) события не создаёт; идемпотентный повтор не дублирует.
- Infrastructure (Testcontainers: PostgreSQL и RabbitMQ): публикатор отправляет события и помечает строки; при остановленном брокере строки остаются, после запуска доходят; ошибка увеличивает `attempts` и сдвигает `next_attempt_at`; после `MaxAttempts` строка получает `dead_at`; два параллельных публикатора не берут одну строку; очистка удаляет только старые опубликованные.
- Потребитель: событие записывается один раз при повторной доставке; неизвестный тип подтверждается; ошибка обработки приводит сообщение в dead-letter очередь.
- Сквозной тест: перевод через API → сообщение в очереди → запись у потребителя.
- `scripts/smoke.sh`: после перевода и пополнения проверить через management API RabbitMQ, что события доставлены (очередь обработана, dead-letter пуста), либо через таблицу потребителя.
- CI: сервис RabbitMQ поднимается в job с тестами и в job stack.

## Вне объёма

Реестр схем, Kafka, транзакционный inbox для HTTP, события регистрации и сброса пароля, отправка уведомлений и Telegram-бот (этап 6), мониторинг метриками (Prometheus).
