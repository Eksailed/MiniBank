# MiniBank: дизайн безопасности и функций (этап 4)

Дата: 2026-11-01

## Цель

Закрыть API: ввести пользователей с входом по email и паролю (JWT), подтверждение email по письму, владение счетами, индивидуальные лимиты на исходящие переводы, а в выписке — фильтр по датам и выгрузку в CSV. Документ продолжает [ядро](2026-10-31-minibank-core-design.md), [корректность](2026-10-31-minibank-correctness-design.md), [веб](2026-10-31-minibank-web-design.md) и [поставку](2026-11-01-minibank-delivery-design.md). Инварианты денег (двойная запись, append-only проводки, идемпотентность, блокировки счетов) не меняются.

## Что решается

Сейчас:

- API открыт: любой, кто знает ID счёта, читает его и двигает деньги.
- У счёта нет владельца, а «мои счета» клиент хранит в `localStorage` и добавляет по ID.
- Нет ограничений на сумму операций.
- Выписка — только постраничный список без фильтров и выгрузки.

## Границы этапа

Входит: регистрация, подтверждение email, вход по JWT, владение счетами, лимиты, фильтрованная выписка и CSV, обновление веб-клиента, Mailpit в Compose, обновление CI.

Не входит: refresh-токены, смена и сброс пароля, роли и админка, двухфакторная аутентификация, надёжная доставка писем (outbox — этап 5), подтверждение смены email.

## Пользователи и аутентификация

### Модель данных

Таблица `users`:

| Поле | Тип | Правила |
| --- | --- | --- |
| `id` | uuid | PK |
| `email` | text | нормализованный (trim + нижний регистр), уникальный индекс, до 254 символов |
| `password_hash` | text | PBKDF2 через `PasswordHasher<User>` (`Microsoft.AspNetCore.Identity`, без полного Identity) |
| `display_name` | text | 1–100 символов после trim, без управляющих символов и NUL |
| `email_confirmed_at` | timestamptz | NULL, пока email не подтверждён |
| `created_at` | timestamptz | |

Таблица `email_confirmation_tokens`: `id` (uuid, PK), `user_id` (FK на `users`, ON DELETE CASCADE), `token_hash` (varchar(64), уникальный индекс), `created_at`, `expires_at`, `used_at` (NULL, пока не использован).

Токен: 32 случайных байта (`RandomNumberGenerator`), в письме в виде base64url. В БД хранится только hex SHA-256 токена; сам токен нигде не сохраняется и не пишется в логи.

### Эндпоинты

| Метод и путь | Что делает | Успех |
| --- | --- | --- |
| `POST /auth/register` `{email, password, displayName}` | Создаёт неподтверждённого пользователя и его токен подтверждения, затем отправляет письмо | 202 |
| `POST /auth/confirm-email` `{token}` | Подтверждает email | 204 |
| `POST /auth/resend-confirmation` `{email}` | Отправляет новое письмо | 202, всегда |
| `POST /auth/login` `{email, password}` | Выдаёт `{accessToken, expiresAt}` | 200 |
| `GET /me` | Профиль `{id, email, displayName}` | 200 |

Правила:

- Пароль: 8–128 символов, без дополнительных требований к составу. Email проверяется простой синтаксической проверкой (одна `@`, непустые части, без пробелов).
- Регистрация с занятым email (в том числе при гонке двух запросов, решает уникальный индекс): 409 `email_taken`. Утечку факта «адрес занят» принимаем осознанно ради простоты.
- Логин: неверный email или пароль — всегда одинаковый 401 `invalid_credentials`. Для несуществующего email выполняется проверка хэша против заглушки, чтобы время ответа не выдавало разницу. Верная пара при неподтверждённом email — 403 `email_not_confirmed`.
- Подтверждение: токен неизвестен, истёк или уже использован — 400 `invalid_confirmation_token`. Успех ставит `email_confirmed_at` и помечает использованными все токены пользователя; операция атомарна, параллельное повторное подтверждение одним токеном успевает только один раз.
- Повторное письмо: ответ 202 одинаков для несуществующего, подтверждённого и обычного адреса. Новое письмо не чаще раза в 60 секунд на пользователя (проверка по `created_at` последнего токена); при отправке предыдущие неиспользованные токены помечаются использованными.
- Срок жизни токена подтверждения: 24 часа.
- Письмо отправляется после коммита транзакции. Если SMTP недоступен, регистрация остаётся успешной, ошибка пишется в лог (без токена и ссылки), пользователь может запросить письмо повторно.
- Ограничение частоты: встроенный `RateLimiter` на группу `/auth/*`, фиксированное окно, `Auth:RateLimitPerMinute` (по умолчанию 10) с одного IP, при превышении 429. Клиентский IP берётся из `X-Forwarded-For`: nginx его передаёт, API учитывает заголовок только от доверенных прокси (`ForwardedHeaders:TrustedNetworks`, в Compose задана сеть контейнеров). Без этого limiter видел бы один адрес nginx и ограничивал всех разом.

### JWT

- Алгоритм HS256. Настройки: `Jwt:Key` (не короче 32 байт, обязателен: без него API не стартует), `Jwt:Issuer` (`minibank`), `Jwt:Audience` (`minibank-web`), `Jwt:LifetimeMinutes` (60). Проверяются подпись, издатель, аудитория, срок; `ClockSkew` 30 секунд.
- Claim `sub` — id пользователя. Других claim-ов с данными пользователя нет.
- В Compose задан dev-ключ; в README сказано, что для любой реальной среды его нужно заменить.
- Глобальная политика авторизации (fallback policy) требует токен для всех эндпоинтов. Открыты только `/auth/*` (кроме `/me`) и `/health`, они помечены `[AllowAnonymous]` явно. Новый эндпоинт без отметки по умолчанию закрыт.
- Отсутствующий, просроченный или неверный токен — 401 в формате `ProblemDetails`.
- Swagger описывает схему Bearer и принимает токен через кнопку Authorize.

## Владение счетами

- В `accounts` добавляется `user_id` (FK на `users`, NULL для системных касс). Ограничение `CHECK (is_system OR user_id IS NOT NULL)` добавляется как `NOT VALID`: существующие тестовые счета остаются без владельца (удалить их нельзя из-за триггеров на проводках) и недоступны через API, а новые обязаны иметь владельца.
- Любой эндпоинт со счётом проверяет владельца. Чужой или без владельца счёт даёт 404, как отсутствующий, чтобы не раскрывать существование ID. Это касается чтения, выписки, CSV, лимитов, пополнения и перевода (счёт списания). Получателя перевода можно указать по ID любого существующего счёта: поведение «получатель не найден» остаётся как сейчас.
- `POST /accounts` принимает `{currency}`; `owner` в записи счёта заполняется `display_name` пользователя на момент создания. Прежнее поле `owner` в запросе удаляется (ломающее изменение контракта; веб-клиент обновляется в этом же этапе).
- Новый `GET /accounts` возвращает счета пользователя с балансами, старые первыми, без пагинации (число счетов пользователя ограничено 50, при превышении `POST /accounts` отвечает 422 `account_limit_reached`).

## Лимиты

- В `accounts` добавляются `per_operation_limit` и `daily_limit` (bigint, в минимальных единицах валюты, > 0, CHECK). У системных касс лимитов нет (значения NULL допустимы только при `is_system`).
- При создании счёта значения берутся из конфигурации `Limits:Default:{RUB|USD|EUR}:{PerOperation|Daily}`. Потолки — `Limits:Max:{валюта}:{PerOperation|Daily}`. Изменение конфигурации не затрагивает уже созданные счета.
- `GET /accounts/{id}/limits` возвращает `{perOperation, daily, spentToday, remainingToday, maxPerOperation, maxDaily}`. `PUT /accounts/{id}/limits {perOperation, daily}` меняет лимиты: значения должны быть > 0 и не выше потолков, иначе 400. Если `daily` меньше `perOperation`, 400.
- Лимиты действуют на исходящие переводы со счёта. Пополнения и входящие переводы не ограничиваются.
- Расход за сутки считается из проводок: сумма модулей отрицательных проводок счёта с `created_at` в текущих сутках по UTC (с 00:00 UTC). Проверка идёт внутри существующей транзакции после блокировки счетов `FOR UPDATE`, поэтому параллельные переводы не пробивают дневной лимит. Отдельных счётчиков нет. Для запроса нужен индекс по `ledger_entries (account_id, created_at)`.
- Превышение возвращает 422: `per_operation_limit_exceeded` или `daily_limit_exceeded`; в теле ошибки указан соответствующий лимит и остаток за сутки. Если превышены оба, возвращается `per_operation_limit_exceeded`.
- Повтор запроса с тем же `Idempotency-Key` возвращает сохранённый ответ и лимиты не проверяет, как и остальные проверки.

## Выписки

- `GET /accounts/{id}/entries` получает необязательные `from`, `to` (ISO 8601, трактуются как UTC; `from` включительно, `to` не включительно) и `direction=in|out` (положительные или отрицательные проводки). Без параметров ответ как сейчас. `from` не раньше `to`, неверное значение `direction` или не разбираемая дата — 400. Пагинация (`page`, `pageSize`) сохраняется.
- `GET /accounts/{id}/entries.csv` принимает те же фильтры, без пагинации. Ответ `text/csv; charset=utf-8` с BOM, разделитель `;`, потоковая запись. Колонки: `Дата (UTC)`, `ID перевода`, `Сумма`, `Валюта`, `Баланс после`. Сумма и баланс в десятичном виде (рубли, а не копейки) с точкой. Свободного текста в файле нет, поэтому CSV-инъекции невозможны. Если нет проводок, в файле только заголовок. Потолок 50 000 строк: при превышении 400 с просьбой сузить период.
- Заголовок `Content-Disposition: attachment; filename="statement-<id>.csv"`.

## Контейнеры и конфигурация

- В `docker-compose.yml` добавляется сервис `mailpit` (`axllent/mailpit`): SMTP 1025 внутри сети Compose, веб-интерфейс на `http://localhost:8025`. Письма наружу не уходят. `api` зависит от `mailpit` (`service_started`).
- Переменные API в Compose: `Jwt__Key` (dev), `Smtp__Host=mailpit`, `Smtp__Port=1025`, `Smtp__From`, `Web__BaseUrl=http://localhost:8080`, `ForwardedHeaders__TrustedNetworks`.
- Настройки SMTP (`Smtp:Host`, `Port`, `Username`, `Password`, `From`, `UseStartTls`) позволяют подставить настоящую почту без изменения кода.
- Nginx веба передаёт `X-Forwarded-For` и `X-Forwarded-Proto` в API.
- Отправка писем: порт `IEmailSender` в `Application`, реализация на MailKit в `Infrastructure`. Тесты подменяют его фейком, который запоминает письма.

## Веб-клиент

- Экраны: «Вход», «Регистрация» (после неё сообщение «письмо отправлено» и кнопка повторной отправки), «Подтверждение email» (`/confirm-email?token=…`, вызывает `POST /auth/confirm-email` и показывает результат), «Выйти».
- Токен в `sessionStorage`; API-клиент добавляет `Authorization: Bearer`. На любой 401 клиент сбрасывает токен и ведёт на вход с возвратом на прежнюю страницу. Защищённые маршруты без токена перенаправляют на вход.
- «Мои счета» берутся из `GET /accounts`. `localStorage`-справочник и форма добавления счёта по ID удаляются; создание счёта — только по валюте.
- Экран счёта: блок «Лимиты» (просмотр, редактирование, остаток за сутки, понятные сообщения об ошибках 400 и 422). Выписка: фильтр по датам и направлению, кнопка «Скачать CSV» (загрузка через `fetch` с токеном и `Blob`, потому что обычная ссылка не передаёт заголовок).
- Типы API перегенерируются из Swagger (`npm run gen:api`).

## Тесты

- **Domain и Application (юнит)**: нормализация и проверка email и имени; проверка пароля; жизненный цикл токена подтверждения (действует, истёк, использован, повторная отправка); расчёт лимитов и остатка.
- **Infrastructure (БД)**: уникальный индекс email; CHECK владельца и лимитов; хранение токенов; запрос расхода за сутки (граница суток UTC, учитываются только списания); индекс.
- **API (интеграционные, Testcontainers)**: полный путь регистрация → письмо (фейковый отправитель) → подтверждение → вход; вход до подтверждения (403); одинаковый 401 для неверного пароля и неизвестного email; отсутствие токена, просроченный токен, токен с неверной подписью (401); 404 на чужой счёт для каждого эндпоинта со счётом; пополнение и списание только на своём счёте; лимиты (на операцию, на сутки, изменение лимитов, потолок, гонка параллельных переводов не пробивает дневной лимит, пополнение не расходует лимит); выписка с фильтрами и ошибками; CSV (BOM, разделитель, заголовок при пустом результате, потолок); rate limit на `/auth/*`; повторное письмо не чаще раза в минуту; параллельная регистрация одного email.
- **Веб (Vitest + MSW)**: вход, регистрация, подтверждение, редирект на 401 с возвратом, список счетов из API, лимиты, фильтр выписки, скачивание CSV.
- **CI**: job `stack` поднимает Compose с Mailpit; `scripts/smoke.sh` проходит сценарий: регистрация, чтение письма через API Mailpit, подтверждение, вход, создание счёта, пополнение, перевод, выгрузка CSV.

## Что проверить отдельно (риски)

- Email с пробелами, в другом регистре, длиннее 254 символов, с юникодом; пароль на границах 8 и 128 символов; имя с управляющими символами.
- Повторное использование и параллельное использование токена подтверждения; истёкший токен; токен чужого пользователя.
- Время ответа логина для существующего и несуществующего email (не должно заметно отличаться).
- Перевод и пополнение с чужого счёта: 404 без раскрытия, деньги не двигаются, ключ идемпотентности не занят.
- Гонка двух переводов, суммарно превышающих дневной лимит; переводы на границе суток UTC; лимит ровно в границу.
- Старые счета без владельца недоступны, при этом миграция применяется на непустой БД.
- Rate limiter за nginx считает клиентов по реальному IP, а не по адресу прокси.
- Токен и ссылка подтверждения не попадают в логи.
