# MiniBank: сброс пароля. Дизайн

## Цель

Пользователь, забывший пароль, запрашивает письмо со ссылкой, задаёт новый пароль и входит. После смены пароля все ранее выданные токены входа перестают работать.

## Что берём из подтверждения email

Сброс повторяет уже работающий механизм подтверждения email, а не изобретает новый:

- токен: случайная строка, в БД хранится только SHA-256 (`ConfirmationTokens.Generate/Hash`), токен одноразовый;
- ответ на запрос письма не выдаёт, зарегистрирован ли email: всегда 202;
- повторный запрос не чаще раза в 60 секунд на пользователя, новый токен гасит прежние;
- ссылка несёт токен во фрагменте URL (`#token=`), на сервер он попадает только в теле POST;
- сбой SMTP не превращает запрос в ошибку и не пишет в лог токен, ссылку или адрес;
- эндпоинты под политикой лимита запросов `RateLimitPolicies.Auth`.

## Домен и БД

- `PasswordResetToken` (таблица `password_reset_tokens`): `Id`, `UserId`, `TokenHash`, `CreatedAt`, `ExpiresAt`, `UsedAt`. Срок жизни 1 час (`Lifetime`), методы `Create`, `IsUsableAt`, `MarkUsed`, как у `EmailConfirmationToken`. Уникальный индекс по `TokenHash`, индекс по `UserId`.
- `User.PasswordChangedAt` (`DateTimeOffset?`, колонка `password_changed_at`) и метод `User.ChangePassword(hash, now)`. Он меняет хэш, ставит `PasswordChangedAt = now` и, если email ещё не подтверждён, подтверждает его: открыв ссылку из письма, пользователь доказал, что владеет почтой.
- Одна миграция: новая таблица и новая колонка.

## Application: `AuthService`

- `ForgotPasswordAsync(email, ct)`: нормализация email (невалидный адрес молча игнорируется); в транзакции `FindByEmailForUpdateAsync`; если пользователя нет или последний токен сброса моложе 60 с, ничего не делает; иначе гасит открытые токены сброса, создаёт новый, после коммита отправляет письмо «Сброс пароля в MiniBank» со ссылкой `{Web:BaseUrl}/reset-password#token=…` и пометкой, что письмо можно игнорировать, если пароль не запрашивали.
- `ResetPasswordAsync(token, newPassword, ct)`: пустой токен или `PasswordPolicy.Validate` не прошли, сначала проверка пароля (`DomainValidationException` → 400), затем в транзакции поиск токена по хэшу; неизвестный, истёкший или использованный токен даёт `InvalidResetTokenException`; иначе `user.ChangePassword(hasher.Hash(...), now)`, гашение всех открытых токенов сброса и открытых токенов подтверждения email пользователя, `SaveChanges`.
- Новое исключение `InvalidResetTokenException` отображается так же, как `InvalidConfirmationTokenException` (400, `ProblemDetails`).
- `IUserRepository`: `FindResetTokenByHashAsync`, `FindLatestResetTokenAsync`, `InvalidateOpenResetTokensAsync`, `Add(PasswordResetToken)`.

## Отзыв старых сессий

JWT остаётся без состояния, но API сверяет его с `PasswordChangedAt`:

- в `AddJwtBearer` добавляется `Events.OnTokenValidated`: по `sub` читается пользователь; если `iat` токена (секунды) раньше `PasswordChangedAt`, усечённого до секунд, токен отклоняется (`context.Fail`), и ответ тот же 401. Отсутствующий пользователь по-прежнему обрабатывается как раньше (эта проверка его не трогает);
- запрос идёт по первичному ключу, одна лёгкая выборка на защищённый запрос; кэша нет, пока это не нужно;
- известная граница: токен, выданный в ту же секунду до смены пароля, проходит проверку; практически это недостижимо, ограничение описывается в README.

## API

- `POST /auth/forgot-password`, тело `{ "email": string }`, всегда 202.
- `POST /auth/reset-password`, тело `{ "token": string, "newPassword": string }`, 204 при успехе, 400 для недействительного токена или слабого пароля.

Контракты добавляются в `Contracts.cs`, типы веб-клиента регенерируются `npm run gen:api`.

## Веб-клиент

- Вход: ссылка «Забыли пароль?» под формой. Маршрут `/forgot-password`: поле Email и кнопка «Отправить ссылку» — это существующий `ResendConfirmation` с новыми пропсами (`action`, `sentText`), так что кулдаун 60 с и обработка ошибок общие. Текст после отправки не выдаёт, существует ли адрес: «Если такой адрес зарегистрирован, мы отправили письмо».
- Маршрут `/reset-password`: токен читается из `location.hash` (как на странице подтверждения); поля «Новый пароль» с индикатором надёжности и «Повторите пароль»; кнопка «Сменить пароль». Успех: экран с зелёной галочкой и кнопкой «Войти». Недействительная ссылка: красная иконка и ссылка «Запросить новую».
- Тексты, стили и компоненты — в духе существующего дизайна (`auth.module.css`, `TextField`, `Button`).
- Токен сессии в `sessionStorage` не трогается: после сброса пользователь входит заново. Если старая сессия отозвана, любой запрос получает 401 и штатно разлогинивает.

## Тесты

- Домен: срок и одноразовость токена, `ChangePassword` подтверждает email и ставит `PasswordChangedAt`.
- Сервис: `forgot` для неизвестного email, для подтверждённого и неподтверждённого, слишком частый запрос, новый запрос гасит прежний токен, сбой SMTP не ломает запрос; `reset` с неверным, истёкшим, использованным токеном, со слабым паролем, успех (старый пароль не работает, новый работает, токен нельзя использовать дважды, email подтверждён).
- API (интеграционные): коды ответов обоих эндпоинтов, 401 для токена, выданного до смены пароля, 200 для токена, выданного после.
- Веб: форма запроса и кулдаун, форма нового пароля (несовпадение паролей, слабый пароль, успех, недействительная ссылка), токен убирается из адресной строки.
- Дымовой скрипт `scripts/smoke.sh`: забыли пароль → письмо в Mailpit → новый пароль → вход со старым 401, с новым 200.

## Вне объёма

Повторный ввод старого пароля при смене из профиля, двухфакторная защита, уведомление о смене пароля письмом.
