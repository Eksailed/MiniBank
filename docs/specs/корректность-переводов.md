# Корректность переводов: идемпотентность и параллельные запросы

Статус: сделано (этап 2). Дата: 2026-10-31.

Связано: план [корректность-переводов.md](../plans/корректность-переводов.md); продолжает [ядро](ядро.md).

## Цель

Сделать переводы безопасными при повторных и параллельных запросах: клиент, повторивший запрос из-за обрыва связи, не должен списать деньги дважды, а одновременные операции над одними счетами не должны отказывать из-за технических конфликтов. Документ продолжает [дизайн ядра](ядро.md); модель данных и инварианты 1–5 этапа 1 не меняются.

## Что решается

Сейчас (итоги ревью этапа 1):

- Повторный `POST /transfers` создаёт второй перевод.
- Системный счёт «Касса» участвует в каждом пополнении и версионируется: из 10 параллельных пополнений разных счетов проходит одно, остальные получают 409 с сообщением «счёт изменён другой операцией», хотя счёт клиента никто не трогал.

## Идемпотентность

Заголовок `Idempotency-Key` **обязателен** для `POST /transfers` и `POST /accounts/{id}/deposit`. Без него или с пустым значением ответ 400. Ключ: строка 1–200 символов без управляющих символов. Остальные эндпоинты не меняются.

### Таблица `idempotency_keys`

| Поле | Назначение |
|---|---|
| `key` (text, PK) | значение заголовка |
| `request_hash` (text) | SHA-256 от «метод, путь, тело запроса»; одинаковые запросы дают одинаковый хеш |
| `status_code` (int) | код сохранённого ответа |
| `response_body` (text) | сохранённый JSON ответа |
| `created_at` (timestamptz) | время записи |

TTL и очистка ключей не входят в этап 2.

### Алгоритм

Всё внутри одной транзакции БД, поэтому ключ и перевод фиксируются атомарно.

1. Открыть транзакцию, выполнить `INSERT INTO idempotency_keys ... ON CONFLICT (key) DO NOTHING`.
2. Вставка прошла: выполнить перевод (см. «Параллельность»), записать в ту же строку ответ и хеш, зафиксировать транзакцию.
3. Ключ уже существует: параллельный запрос с тем же ключом ждёт на уникальном индексе, пока первый не завершится. После этого прочитать строку:
   - хеш совпадает: вернуть сохранённые код и тело; добавить заголовок `Idempotent-Replayed: true`; новый перевод не создаётся;
   - хеш другой: 422 («ключ уже использован с другим запросом»).
4. Если операция завершилась бизнес-ошибкой (400/404/422 и т. п.), транзакция откатывается вместе с ключом. Повтор с тем же ключом выполняется заново: баланс мог измениться. Сохраняются только успешные ответы.

## Параллельность

Перевод и пополнение выполняются в явной транзакции. Участвующие счета (для пополнения: счёт клиента и касса нужной валюты) блокируются **одним запросом** `SELECT ... FROM accounts WHERE id = ANY(@ids) ORDER BY id FOR UPDATE`. Фиксированный порядок по `id` исключает взаимные блокировки при встречных переводах A→B и B→A. Параллельные операции с одной кассой выстраиваются в очередь и завершаются успешно, а не получают 409.

Оптимистичная блокировка по `accounts.version` остаётся как страховка. Если PostgreSQL всё же сообщает об ошибке сериализации или взаимной блокировке (SQLSTATE `40001`, `40P01`), операция повторяется целиком, до 3 попыток; после этого клиент получает 409 как раньше.

Блокировка берётся до проверок бизнес-правил, чтобы проверка баланса шла по актуальному значению.

## Тесты

Порядок: сначала красные тесты, воспроизводящие проблему, затем исправление.

- **Гонка на кассе:** 50 параллельных пополнений разных счетов одной валюты: все 200, итоговый баланс каждого счёта равен сумме пополнений. (До исправления большинство получает 409.)
- **Шторм переводов:** сотни параллельных переводов между 5 счетами в обе стороны (включая встречные пары); по завершении сумма всех балансов равна нулю, ни один клиентский баланс не отрицателен, баланс каждого счёта равен сумме его проводок, у каждого перевода ровно две проводки с суммой 0; тест не зависает (нет взаимных блокировок).
- **Идемпотентность:** повтор запроса с тем же ключом возвращает тот же ответ и заголовок `Idempotent-Replayed`, создан один перевод, баланс изменён один раз; тот же ключ с другим телом даёт 422; 20 параллельных запросов с одним ключом создают ровно один перевод; запрос без ключа даёт 400; неуспешный запрос (недостаточно средств) не занимает ключ.
- Существующие тесты этапа 1 получают заголовок через общий помощник.

## Мелочи из ревью этапа 1

Входят в этап 2:

- Новая миграция: триггер `ledger_entries_append_only` срабатывает также на `TRUNCATE`. `InitialCreate` не редактируется, он уже опубликован.
- `Account.Debit` и `Account.Credit` становятся `internal` (с `InternalsVisibleTo` для тестов домена), чтобы проводки создавались только через `Transfer`.
- Бизнес-ошибки (400/404/409/422) не пишутся в лог как Error; 500 логируется один раз.
- Версии `Npgsql.EntityFrameworkCore.PostgreSQL` и `EFCore.NamingConventions` закрепляются.
- README: раздел про идемпотентность и параллельность, обновлённая таблица API (заголовок `Idempotency-Key`, код 422 для конфликта ключа).

Остальные minor-замечания ревью (точность времени, текст ошибок привязки модели, пробелы в покрытии 4xx) остаются в списке отложенных.

## Вне этапа 2

TTL и очистка ключей; ключи на `POST /accounts`; JWT, лимиты, выписки с курсорной пагинацией (этап 4); outbox (этап 5).

## Критерии готовности

- Повтор запроса с тем же ключом не создаёт второй перевод.
- Параллельные пополнения и переводы не получают 409 из-за кассы и не блокируют друг друга навсегда.
- Инварианты 1–5 соблюдаются после шторма параллельных операций.
- Все тесты проходят локально; README описывает новое поведение.
