# Уведомления в Telegram: привязка чата, настройки, доставка с повторами

Статус: сделано (этап 6). Автотесты зелёные: Domain 86, Notifications 64, Infrastructure 171, Api 181, web 204. С настоящим ботом вручную пока не проверялось: нужен токен от @BotFather.
Связано: [план реализации](../plans/2026-11-02-minibank-telegram-notifications.md), раздел «Уведомления в Telegram» в [README](../../README.md).

## Цель

Этап 6 роадмапа. Пользователь привязывает Telegram в профиле веб-клиента и получает сообщения о переводах и пополнениях; в профиле же включает и выключает уведомления и выбирает типы событий. Источник данных — события этапа 5 (`transfer.completed`, `account.deposited`), которые потребитель `MiniBank.Notifications` уже принимает с дедупликацией.

## Что решили

- Только настоящий бот: токен обязателен, фейкового сервера Telegram нет. Бот получает апдейты через long polling (`getUpdates`), вебхуки не нужны.
- Сервис `notifications` без токена не стартует. В Compose он вынесен в профиль `telegram`: `docker compose up` его не поднимает, `docker compose --profile telegram up` поднимает (токен в `TELEGRAM_BOT_TOKEN`, имя бота в `TELEGRAM_BOT_USERNAME`). CI проверяет остальной стек, как на этапе 5.
- Веб ходит только в API. API владеет пользовательскими эндпоинтами, `notifications` владеет таблицами (схема `notifications`) и внутренним HTTP API. API вызывает его по внутренней сети с общим секретом.
- Команд бота (`/balance` и т.п.), вебхуков, нескольких чатов на пользователя и событий регистрации/сброса пароля в этапе нет.

## Как это устроено

```
Web ──JWT──► API ──внутренний HTTP + секрет──► Notifications ◄──► Telegram Bot API (long polling)
                                                   ▲
                       RabbitMQ ──события──────────┘ ──► PostgreSQL (схема notifications)
```

`MiniBank.Notifications` переходит с Worker SDK на Web SDK: внутри один процесс с тремя частями.

1. **Потребитель событий** (как сейчас): пишет `received_events`, затем для каждого владельца ставит доставку в очередь `telegram_deliveries`, если у него есть привязка и событие разрешено настройками. Запись события и постановка доставок выполняются в одной транзакции.
2. **Отправитель**: фоновый сервис берёт доставки `FOR UPDATE SKIP LOCKED`, шлёт `sendMessage`, отмечает результат.
3. **Бот и внутренний API**: polling `getUpdates` обрабатывает `/start <код>`; внутренние эндпоинты обслуживают API.

## Внутренний API сервиса notifications

Доступен только из сети Compose (порт наружу не публикуется); каждый запрос несёт заголовок `X-Internal-Secret`, сравнение в постоянное время. Секрет — `Notifications__InternalSecret` (в Compose демонстрационный, переопределяется через env, как JWT-ключ).

| Метод и путь | Назначение |
|---|---|
| `GET /internal/users/{userId}/telegram` | статус привязки и настройки |
| `POST /internal/users/{userId}/telegram/link-code` | выпуск кода привязки, ответ: ссылка `https://t.me/<bot>?start=<код>` и срок действия |
| `DELETE /internal/users/{userId}/telegram` | отвязка |
| `PUT /internal/users/{userId}/telegram/settings` | изменение настроек |

## Эндпоинты API для веба

Требуют JWT, лимит запросов такой же, как у остальных.

`GET /me/notifications`, `POST /me/notifications/telegram/link`, `DELETE /me/notifications/telegram`, `PUT /me/notifications/settings`. `userId` берётся из токена и никогда из тела запроса. Если `notifications` недоступен, эти эндпоинты отвечают `503` (ProblemDetails), остальной API не затронут, `/health` не зависит от `notifications`.

## Данные

Схема `notifications`, новая миграция.

- `telegram_links(user_id PK, chat_id UNIQUE, linked_at)`.
- `link_codes(code_hash PK, user_id, expires_at)`: хранится SHA-256 кода, код — 128 бит случайности, одноразовый, TTL 10 минут. У пользователя не больше одного активного кода: новый заменяет прежний.
- `notification_settings(user_id PK, enabled, on_transfer_sent, on_transfer_received, on_deposit)`; по умолчанию всё `true`. Строка создаётся при первом изменении, отсутствие строки означает значения по умолчанию.
- `telegram_deliveries(id PK, received_event_id FK, chat_id, text, status, attempts, next_attempt_at, sent_at, last_error)`, уникальный индекс по `received_event_id`; статусы `pending`, `sent`, `failed`.

Тексты формируются один раз при постановке в очередь, на русском, без имён и email: «Перевод: −2 500,00 ₽», «Поступление: +2 500,00 ₽», «Пополнение: +10 000,00 ₽». Сумма хранится в событии в минорных единицах и форматируется из неё.

## Как привязывается чат

1. Пользователь нажимает «Привязать Telegram»; API запрашивает код, веб показывает ссылку и подсказку.
2. Пользователь открывает ссылку и нажимает Start; бот получает `/start <код>`.
3. Сервис находит неистёкший код по хешу, в одной транзакции удаляет код и создаёт или заменяет привязку (`chat_id` уникален: если он уже привязан к другому пользователю, привязка переходит к новому, прежняя снимается), отвечает «Готово».
4. Неверный, просроченный или повторно использованный код: ответ «Код недействителен», привязки нет. Любое другое сообщение боту: короткая справка.

Веб опрашивает статус (`GET /me/notifications`) раз в несколько секунд, пока открыто окно привязки.

## Что делаем при сбоях

- Сбой Telegram не затрагивает обработку события: доставка остаётся в очереди, событие подтверждается и не попадает в dead-letter.
- Ошибка отправки: `attempts++`, пауза `5с·2^(n−1)` до 5 минут, при `429` учитывается `retry_after`. После 10 попыток статус `failed`. Недоступность Telegram попытки не тратит (как недоступность брокера на этапе 5): пачка прерывается, строки ждут.
- `403 Forbidden` (бот заблокирован) снимает привязку, доставка получает `failed`.
- Дубль события не создаёт вторую доставку (уникальный индекс).
- Отправленные и `failed` доставки старше 30 дней удаляются фоново.
- Токен бота не попадает в логи (в том числе в URL запросов и сообщения исключений).

## Что видит пользователь в вебе

Карточка «Уведомления в Telegram» в профиле: статус (привязано / нет), кнопка «Привязать» со ссылкой и подсказкой, переключатели «Уведомления», «Исходящие переводы», «Входящие переводы», «Пополнения», кнопка «Отвязать». Состояние 503 показывается как «Сервис уведомлений временно недоступен».

## Как проверяем

- Юнит-тесты: формирование текстов, фильтр по настройкам, хеширование и срок действия кода, расчёт паузы.
- Интеграционные тесты (Testcontainers PostgreSQL и RabbitMQ, заглушка HTTP вместо Telegram Bot API): привязка по коду (успех, просрочен, повтор, чужой чат), событие → доставка → `sendMessage`, дубль события, `429` и повтор, недоступный Telegram не тратит попытки, `403` снимает привязку, настройки отключают типы.
- Сквозной тест (API + notifications + заглушка): перевод через API доходит как сообщение с верным текстом.
- Веб-тесты: Vitest для карточки (статусы, переключатели, 503).
- Smoke и CI без токена проверяют остальной стек; бот проверяется вручную с настоящим токеном (инструкция в README).

## Review Focus: на что смотреть при ревью

1. Один `chat_id` не может получать уведомления двух пользователей; перепривязка не оставляет старого владельца.
2. Код привязки нельзя использовать дважды и после истечения; перебор не даёт подсказок.
3. Недоступность Telegram не теряет события и не уводит их в dead-letter; доставка уходит после восстановления.
4. Заблокированный бот снимает привязку, а не крутит бесконечные повторы.
5. Токен бота и секрет внутреннего API не попадают в логи и ответы.

## Чего в этапе нет

Команды бота, вебхуки, несколько чатов на пользователя, уведомления о регистрации и сбросе пароля, шаблоны и локализация текстов, метрики (Prometheus).
