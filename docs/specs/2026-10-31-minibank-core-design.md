# Ядро MiniBank: счета, переводы с двойной записью, выписка

Статус: сделано (этап 1). Дата: 2026-10-31.

Связано: план [2026-10-31-minibank-core.md](../plans/2026-10-31-minibank-core.md); следующий этап — [корректность](2026-10-31-minibank-correctness-design.md).

## Цель

Учебный банковский бэкенд на .NET для портфолио (стажировка .NET-разработчика). Нужен проект, который можно показать и разобрать на интервью: автор объясняет любое решение в коде, репозиторий запускается одной командой и покрыт тестами. Деньги не настоящие, работа одиночная, UI не нужен.

Этот документ описывает **этап 1** (ядро). Этапы 2–6 перечислены в конце и получают свои спецификации отдельно.

## Подход

Модульный монолит со слоями Domain / Application / Infrastructure / Api. Выделение отдельных сервисов (уведомления) откладывается на поздние этапы. Микросервисы с первого дня и простой CRUD отвергнуты: первые уводят время в инфраструктуру, вторые не показывают тем финтеха (транзакции, идемпотентность, конкурентность).

## Стек

C#, ASP.NET Core (.NET 9), PostgreSQL, EF Core + Npgsql, Docker. Тесты: xUnit, Testcontainers.

## Модель данных

### Деньги

Сумма хранится как `bigint` в минимальных единицах (копейки) вместе с кодом валюты. `decimal` и `float` не используются. Одна валюта на счёт; переводы возможны только между счетами одной валюты. Конвертации нет.

### Таблицы

| Таблица | Поля |
|---|---|
| `accounts` | `id` (uuid), владелец, `currency`, `balance` (кэш), `version` (оптимистичная блокировка), `status`, `is_system`, `created_at` |
| `transfers` | `id`, `from_account_id`, `to_account_id`, `amount`, `currency`, `status`, `created_at` |
| `ledger_entries` | `id`, `transfer_id`, `account_id`, `amount` (знаковая: списание отрицательное, зачисление положительное), `balance_after`, `created_at` |

В `transfers` хранятся только выполненные переводы. Колонка `status` остаётся на будущее; в этапе 1 всегда `Completed`. Неудавшиеся по бизнес-правилам переводы не сохраняются, клиент получает ошибку.

### Инварианты

Защищаются доменной логикой, ограничениями БД и тестами.

1. Каждый перевод создаёт ровно две проводки, сумма которых равна нулю (двойная запись).
2. Проводки только добавляются. Изменение и удаление запрещены; исправление делается новой встречной операцией.
3. Источник истины — проводки. `accounts.balance` является кэшем, обновляется в той же транзакции, что и проводки, и всегда равен сумме проводок по счёту. Это проверяется тестом.
4. Баланс обычного счёта не опускается ниже нуля (`CHECK` в PostgreSQL и проверка в домене).
5. Деньги входят в систему и выходят из неё через системный счёт «Касса» (`is_system = true`), которому разрешён отрицательный баланс. Пополнение — обычный перевод с кассы на счёт клиента. Сумма всех балансов в системе всегда равна нулю. Счёт «Касса» создаётся миграцией.

### Вне рамок этапа 1

Мультивалютность, комиссии, отмена переводов, аутентификация.

## Архитектура

Зависимости направлены внутрь: Api → Application → Domain; Infrastructure → Application, Domain.

| Проект | Ответственность |
|---|---|
| `MiniBank.Domain` | `Money`, `Account`, `Transfer`, `LedgerEntry`, доменные исключения. Без внешних зависимостей; вся бизнес-логика здесь |
| `MiniBank.Application` | Сценарии (создать счёт, пополнить, перевести, получить баланс, получить выписку), интерфейсы репозиториев, `IUnitOfWork`. Сценарии — обычные классы, без MediatR |
| `MiniBank.Infrastructure` | EF Core, Npgsql, миграции, реализации репозиториев |
| `MiniBank.Api` | ASP.NET Core с контроллерами, OpenAPI/Swagger, middleware обработки ошибок |
| `*.Tests` | Юнит-тесты домена; интеграционные тесты API на реальном PostgreSQL (Testcontainers) |

Контроллеры выбраны вместо minimal API, потому что чаще встречаются в проектах компаний.

## API (этап 1)

| Метод | Назначение |
|---|---|
| `POST /accounts` | Создать счёт |
| `GET /accounts/{id}` | Счёт и баланс |
| `POST /accounts/{id}/deposit` | Пополнить счёт (внутри — перевод с кассы) |
| `POST /transfers` | Перевод между счетами |
| `GET /accounts/{id}/entries` | Выписка с постраничной загрузкой |

## Поток перевода

`POST /transfers` с телом `{fromAccountId, toAccountId, amount, currency}`:

1. Проверка входных данных: сумма больше нуля, счета различаются, валюта совпадает.
2. Открывается транзакция БД, загружаются оба счёта.
3. Домен выполняет `from.Debit(amount)` и `to.Credit(amount)`: проверяет статус счёта и достаточность средств, создаёт две проводки с `balance_after`.
4. В той же транзакции сохраняются `Transfer`, две проводки и новые балансы; коммит.

### Конкурентность

В этапе 1 применяется оптимистичная блокировка: у счёта есть `version`, при конфликте запрос получает 409. Усиление (пессимистичные блокировки и ретраи) — тема этапа 2.

## Обработка ошибок

Все ошибки возвращаются в формате `ProblemDetails` через общий middleware.

| Ситуация | HTTP-код |
|---|---|
| Невалидный ввод | 400 |
| Счёт не найден | 404 |
| Недостаточно средств, счёт заблокирован | 422 |
| Конфликт версий | 409 |

## Тестирование

- Юнит-тесты `Money` и `Account`, включая свойства: сумма проводок перевода равна нулю, дебет не уводит баланс ниже нуля.
- Интеграционные тесты по всем эндпоинтам на настоящем PostgreSQL (Testcontainers).
- Сверочный тест после серии операций: сумма всех балансов равна нулю; баланс каждого счёта равен сумме его проводок.

## Критерии готовности этапа 1

- Все эндпоинты из раздела API работают и описаны в Swagger.
- Инварианты 1–5 соблюдаются и проверены тестами.
- Миграции создают схему и системный счёт «Касса».
- Все тесты проходят локально.
- README описывает запуск и содержит схему данных.
